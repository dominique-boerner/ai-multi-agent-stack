# ai-multi-agent-stack

## Project Overview
This repository contains the `ai-multi-agent-stack`, a highly scalable Multi-Agent System (MAS) built with Node.js and TypeScript. The system leverages Google Gemini models (via the Google Gen AI SDK) to simulate and automate a complete software development lifecycle.

The core feature of this stack is its **configuration-driven architecture**. Instead of hardcoding agents into the application logic, they are instantiated dynamically via a central configuration file. This allows the development team to be scaled up or customized effortlessly.

## API & Entry Point (REST)
Interaction with the system does not happen via a command line, but through a standardized REST API. Users submit their requests as a JSON payload to a `POST` endpoint. A web server (e.g., Express.js or Fastify) receives the request and triggers the Orchestrator.

**Example Request:**
` ` `http
POST /api/v1/projects/generate
Content-Type: application/json

{
  "user_prompt": "Build a REST API for a Todo list using Node.js and save the data in a local JSON file.",
  "additional_context": "Please ensure clean error handling and use TypeScript interfaces."
}
` ` `

## System Architecture & Core Requirements

The system is event-driven and divided into three logical layers:

1.  **Orchestration Layer:** A central Orchestrator (Supervisor) receives the REST payload, manages the control flow, maintains the global status (Shared State), and routes tasks based on the capabilities of the configured agents.
2.  **Requirement Layer:** A Product Owner (PO) translates vague user ideas into structured, actionable tickets.
3.  **Implementation Layer (Development & Review):** A pool of Developer agents translates the tickets into code. An integrated review process forces the agents to peer-review each other's code (or uses a dedicated Reviewer) before a feature is marked as "done".

## Configuration (`agent-stack.config.mjs`)
The entire agent team is managed centrally via an array in the configuration file. To expand the team, simply add a new agent object to the array.

` ` `javascript
export const agentConfig = {
  orchestrator: {
    model: "gemini-pro",
    strategy: "capability_routing", // Routes tickets to capable agents
  },
  agents: [
    {
      id: "po_main",
      role: "product_owner",
      capabilities: ["write_tickets"]
    },
    {
      id: "dev_backend",
      role: "developer",
      capabilities: ["write_code", "read_tickets"]
    },
    {
      id: "reviewer_senior",
      role: "reviewer",
      capabilities: ["review_code"]
    }
  ]
};
` ` `

## Agent Roles in Detail

### 1. Orchestrator (Router / Supervisor)
* **Task:** Starts the workflow upon receiving the `POST` request. It reads `agent-stack.config.mjs`, assembles the team, and orchestrates the message queue between the agents.
* **Logic:** Triggers the PO, receives its tickets, searches the agent pool for suitable developers, and enforces the review cycle. Once the cycle is complete, it can send a response back to the API caller (e.g., via webhooks or Server-Sent Events).

### 2. Product Owner (PO)
* **Task:** Analyzes the `user_prompt` from the API and breaks it down into business requirements.
* **Output:** Generates structured tickets (JSON) containing user stories, acceptance criteria, and technical specifications.

### 3. Developer (Pool)
* **Task:** Reacts to assigned tickets. Develops architectural concepts and writes clean, testable code (TypeScript/Node.js).
* **Behavior:** Developers work in isolation on the ticket and return the finished code to the Orchestrator for review.

### 4. Reviewer (Peer-Review)
* **Task:** Reviews the code generated by the developers for bugs, best practices, and fulfillment of the acceptance criteria.
* **Output:** Responds with a strict status (`APPROVE` or `REJECT`) along with detailed feedback for the developer if revisions are necessary.

## Workflow (Feature Lifecycle)

1.  **Init:** The server is running, and the Orchestrator has the config ready.
2.  **Input:** The client sends a `POST` request with the project idea to the API.
3.  **Definition:** The Orchestrator triggers the PO. The PO writes tickets and saves them to the `SharedState`.
4.  **Assignment:** The Orchestrator detects new tickets and assigns them to the developer agents (e.g., backend ticket to `dev_backend`).
5.  **Development:** The developer generates the code and reports "Ready for Review".
6.  **Review Loop:**
    * The Orchestrator routes the code to `reviewer_senior`.
    * **If REJECT:** The ticket is sent back to the developer along with a bug report (Step 5 repeats).
    * **If APPROVE:** The code is accepted and saved locally to the workspace. Success is reported back to the client.

## Known Challenges & Technical Considerations

To ensure the system remains stable in production, the following edge cases should be considered during implementation:

1.  **Infinite Review Loops:** If a Reviewer repeatedly rejects the Developer's code without the Developer being able to fix it, the system can get stuck in an endless loop.
    *   *Solution:* Implement a "Max-Retry" counter (e.g., max 3 iterations) in the Orchestrator. If the limit is reached, gracefully abort the task or escalate to a human operator.
2.  **Structured Output (JSON Hallucinations):** LLMs tend to add conversational filler text (e.g., "Here is your JSON:") even when asked for strict JSON.
    *   *Solution:* Leverage the *Structured Output* (JSON Schema) features of the Gemini API to enforce strict adherence to the expected data structures for PO tickets and Reviewer responses (`APPROVE`/`REJECT`).
3.  **Context Window & Token Costs:** Passing the entire `SharedState` (tickets, full codebase, complete review history) back and forth can quickly lead to high costs and context limits.
    *   *Solution:* Implement smart prompt construction in the Orchestrator. Send agents only the state they actually need to perform their particular task based on their capabilities.
4.  **Missing Execution Environment:** Developers currently write code purely theoretically, and the Reviewer analyzes it statically. There is no automated test execution.
    *   *Future Enhancement:* Integrate an isolated Sandbox environment (e.g., Docker) where tests can actually run. This enables test-driven development functionality before the code goes to the Reviewer.
